Three ways to make one agent become many

The RLM POC, Claude Code Workflows, and Copilot Fleet all fan work out across agents. They disagree about one thing: who decides the shape of the fan-out. RLM lets the model decide, recursively, at run time. Workflows freeze the shape into a JavaScript program before any agent starts. Fleet lets the model decide once, flat, inside a single session. Everything else below follows from that.

01

The shape of the fan-out

Same job, three topologies. Depth, symmetry, and who draws the arrows.

RLM POC

recursive tree

The model draws the tree while it runs.

Every rlm call opens a fresh in-process Copilot SDK session with rlm re-registered — so it can recurse again. Each child gets a clean slate, a profile (model policy + tool allowlist + skill bundle), and a written authority envelope. invoke_trellage is the escape hatch to a real terminal harness; that branch is always a leaf.

Claude Workflows

scripted DAG

You draw the tree before it runs.

The topology is a JavaScript program, not a prompt. pipeline() runs each item through all stages with no barrier; parallel() is the barrier when you truly need every result at once. Agents return schema-validated objects, so dedupe/count/branch is ordinary code. Nesting is one level.

Copilot Fleet

flat swarm

The model draws one flat row, once.

fleet.start does not build a graph — it injects an orchestration prompt into a live session and flips it into parallel subagent execution (also reachable as the autopilot_fleet exit from plan mode). Subagent types come from .agents/. It is the lowest-ceremony option by a wide margin, and the only one a human watches in real time.

03

Pros and cons

Each system's cons are the direct price of its pros.

RLM POC

weavekit

Pros

  • Only one that crosses vendors. A single run can use Copilot routing, a Claude Code agent loop, and a Codex launcher. Neither competitor can leave its own house.
  • Unbounded shape. Adaptive depth handles work whose decomposition is unknown until you are inside it.
  • Capability governance is real, not advisory: fail-closed skill boundaries, per-profile tool allowlists, explicit read-only vs write authority, mandatory specialization (a research child that skipped its skill is rejected).
  • Best isolation. Managed worktrees, per-repo mutex, automatic reclamation — the user's checkout is never touched.
  • Best model routing. Live catalog, capability/modality requirements, fallbacks, dry-run inspection, plus per-profile model preference.
  • Genuinely unattended. Questions are answered from root context; hard blocks escalate over Telegram instead of stalling.
  • Deepest tracing. The Langfuse span tree is the recursion tree.

Cons

  • Non-deterministic and unreproducible. Two runs of the same prompt can produce different trees. No prefix-cached resume — a resume starts a fresh budget.
  • Cost is hard to predict. Depth × branching under a shared budget; the ceiling is a call count, not a token count.
  • No typed results. Parents parse prose, so failures degrade quietly rather than being caught at a schema boundary.
  • The invoke_trellage leg is heuristic. It needs a PTY (untestable headless), pays ~40 s container boot, and detects completion from a result file plus three identical screen frames. A harness that never writes the file times out.
  • Large operational surface. Herdr, Trellage, worktrees, skill caches keyed to upstream HEAD, a loopback proxy, Langfuse, Telegram — many things that can be down.
  • Answered-for-you questions can be confidently wrong. The answerer sees the root snapshot, not the truth.
  • POC. Not a supported product surface.

Claude Workflows

claude code

Pros

  • Deterministic and reviewable. The orchestration is source code — diffable, testable, re-runnable, explainable to someone else.
  • Prefix-cached resume is the standout feature. Edit stage 3 and stages 1–2 return instantly from the journal. Nothing else here has this.
  • Typed hand-offs. Schema validation at the tool layer means the child retries itself, and cross-agent logic (dedupe, vote counting, early exit) is plain JS with no parsing.
  • Latency-aware primitives. pipeline() avoids the barrier stall that naive fan-out/fan-in designs pay on every stage.
  • Real budget control. Hard token ceiling that scripts can query and loop against (budget.remaining()).
  • Quality patterns compose: adversarial refutation, judge panels, loop-until-dry, completeness critics — all expressible because control flow is code.

Cons

  • You must know the shape first. Unknown decompositions force a scout-then-run hybrid across turns.
  • Single vendor, single harness. No path to Codex, Copilot, or a container profile.
  • Depth capped at two. Nested workflow() cannot nest again.
  • Authoring friction. Plain JS, no TypeScript, no filesystem, and Date.now()/Math.random() throw — small rules that bite when you forget them.
  • Weak write isolation by default. Parallel mutating agents collide unless you opt into per-agent worktrees, which cost setup time and disk.
  • Failures are silent nulls. A dead agent becomes null in the result array; forget .filter(Boolean) and you get a wrong answer, not an error.
  • Can burn a lot of tokens fast, which is why it needs explicit opt-in.

Copilot Fleet

copilot cli

Pros

  • Lowest friction that exists. One RPC call, or one selection when leaving plan mode. No script, no profile, no worktree plumbing.
  • Human stays in control. Live TUI, structured lifecycle events, real approvals, interrupt at any point.
  • Plan-mode continuity. The plan the model just wrote becomes the fan-out — no translation step where intent gets lost.
  • Cheap coordination. One session, one context, one working tree: no cross-process state to reconcile.
  • Uses existing .agents/ definitions — the same subagents you already invoke by hand.
  • First-class in the product, not a bolt-on.

Cons

  • Flat only. No recursion, no depth, no sub-decomposition — hierarchical work has to be flattened by hand.
  • No write isolation. Parallel subagents editing one checkout is the obvious failure mode, and nothing structurally prevents it.
  • Not reproducible and not resumable as a graph. The fan-out lives in a prompt, so you cannot diff it, replay it, or partially re-run it.
  • No typed results and no cross-agent logic layer — the main agent reconciles everything in natural language, in its own context window.
  • Weakest budget story. No surfaced fan-out cap or token ceiling.
  • Single vendor, and orchestration quality depends entirely on the injected prompt.
  • Experimental, and interactive-only in practice.
04

Which to reach for

These are complements, not competitors.

Pick RLM when…

  • the job needs a capability that only another vendor's harness has
  • the decomposition is unknown until you are inside it
  • you need capability containment — read-only workers, forced specialization
  • it must run unattended and reach you only when truly blocked
  • parallel work must not touch your checkout

Pick Workflows when…

  • you already know the shape: N dimensions, M verifiers, one synthesis
  • you will run it more than once and want to iterate on the orchestration
  • you need typed results and real cross-agent logic (voting, dedupe, exit)
  • the token budget must be enforced, not hoped for
  • a stage will change and you want the earlier stages back for free

Pick Fleet when…

  • you are already in the session and just planned the work
  • the work is obviously parallel and shallow
  • you want to watch and interrupt rather than review afterwards
  • writing an orchestration script would cost more than the task
  • subagents mostly read, so a shared checkout is safe

The short version

Fleet is the cheapest way to go parallel and the only one a human supervises live — but it is flat, unisolated, and unrepeatable. Workflows is the only one where the orchestration is an artifact you can diff, test, budget, and partially re-run — at the cost of having to know the shape in advance and staying inside one vendor. RLM is the only one that can recurse to arbitrary depth and reach outside its own vendor, with the strongest containment and isolation of the three — at the cost of determinism, predictable spend, and a large operational surface that is still a prototype.

They stack cleanly: Fleet inside a session, Workflows for repeatable structure, RLM when the work must leave the harness. The interesting gap RLM has not closed is the one Workflows solved — a typed, resumable, deterministic record of what the tree actually did.
