Drop the Pane

The RLM orchestrator types tasks into a terminal and reads the screen back. It does not have to. Every harness it drives runs headless and returns structured JSON.

Decision. Stop driving delegated harnesses through a Herdr-owned PTY. Run them with execFile and -p, and read the result event. Delete the drive loop, the screen classifier, and the Herdr backend. Keep the worktree isolation, the catalog, the budget accounting, and the Langfuse spans.

02

The claim this overturns

Refuted

ADR 0011 states that container mode cannot be driven by pipes or execFile at all, and that only the non-interactive subcommands run headless. That is the premise the whole PTY design rests on.

The launcher itself disagrees. /Users/smendenh/.local/bin/trellage, lines 722-725, exempts prompt mode from its own TTY assert: 

if [[ "$mode" != prompt && "$mode" != stop && "$mode" != doctor && "$mode" != destroy \
  && "$mode" != memory-status && "$mode" != memory-sync ]]; then
  [[ -t 0 && -t 1 ]] || fail 'an interactive terminal is required'
fi

trellage --profile X --prompt is headless-legal. So is every native launcher. ADR 0010's original judgement — Trellage is headless-feasible in one-shot -p mode — was correct. ADR 0011 overturned it on a false premise.

05

How the orchestrator answers questions

The part that needs the most care. It is simpler than expected, because of one finding.

Neither harness can ask a question in headless mode. Claude has no AskUserQuestion; Copilot has no ask_user. Both verified above.

So the design problem is not “detect a question and answer it”. There is no question to detect. The correct framing is:

The run ends. Work out whether it achieved the goal. If it did not, work out what it lacked, supply that, and resume the same session.

This is a better problem than the one we have today. The signal is a structured field, not a terminal screen.

Highest risk

“success: true” does not mean the goal was met

The harness reports “I completed my turn”, not “I achieved your goal”.

The Copilot run in section 03 returned success: true alongside a summary saying it could not do the thing. Claude behaves the same way: subtype: "success" with is_error: false on a turn that gave up. Any classifier that trusts the boolean alone is wrong. Test this first, and test it hardest.

Three tiers

Tier 1 · always

Front-load the brief

Put everything the delegate could need into the task before launch, and add one rule: you cannot ask questions; if you lack something, say so in your summary prefixed NEEDS: and finish your turn. This turns an implicit failure into a greppable one. It costs nothing.

Tier 2 · build this

Classify, answer, resume

Terminate → read the structured outcome → diagnose what it lacked → the orchestrator answers → resume the same sessionId. Each attempt spends one unit of the existing shared call budget, so the loop is bounded by the same budget that bounds recursion.

Tier 3 · defer

Bidirectional control

Claude has --input-format stream-json — a real in-turn channel over stdin, no PTY. Unverified Copilot has no equivalent. Build it only if Tier 2 proves insufficient in practice.

The Tier 2 loop

delegate(profile, brief, budget):
  sessionId = uuid();  attempt = 1;  history = []

  loop:
    budget.consume()                    # a resume costs the same as a call
    raw     = run(profile, prompt, sessionId, resume = attempt > 1)
    outcome = classifyStructured(raw)   # exit code + terminal event ONLY — pure

    if outcome is COMPLETED_CLEAN:   return success(raw)
    if outcome is PROCESS_FAILURE:   return failure(outcome, raw)
    if attempt >= maxAttempts:       return failure(TURN_LIMIT, history)

    need = diagnose(raw)                # reads NEEDS:, then the summary text
    if need is NONE:                 return failure(UNCLASSIFIABLE, history)

    prompt  = orchestratorAnswer(need)  # reuse createTrellageAnswerer unchanged
    attempt += 1

classifyStructured is pure and fully unit-testable against recorded JSONL. diagnose is the only place a model is involved, and it reads a structured summary paragraph — never a terminal screen. When the summary carries a NEEDS: prefix, diagnose makes zero model calls.

What we give up, honestly

Today handleBlocked catches a TUI question and answers it mid-run. But look at what that answerer is: it spins a fresh Copilot session grounded in a snapshot of the root conversation and answers on the root's behalf. It is a model answering a model. It was never the operator.

So we lose an in-turn model round trip. We do not lose a human decision. And --resume recovers the capability across turns instead of within one.

06

Test plan

The headless path is far more testable than the PTY path, because the input is a recorded JSON stream instead of a live terminal.

Fixtures first

Capture real JSONL from every reachable launcher into tests/rlm-poc/trellage/fixtures/headless/, one file per scenario per harness. These replace the recorded-screen fixtures that screen.test.ts uses today.

The priority test

Feed diagnose the verbatim Copilot fixture from section 03 — success: true with a summary saying the goal was not achieved. Assert the diagnosis is needs-information, not achieved. If that test does not exist, the migration is not done.

Fixture Expected diagnosis
NEEDS: the database connection string needs-information, need extracted, zero model calls
success true, summary says goal met achieved
success true, summary says "I could not find X" needs-information
success true, summary says "I chose not to, because Y" refused
success false, with a summary blocked
empty summary blocked — obstacle "no summary produced"
summary is only a file path achieved if the file exists in the worktree, else blocked

Beyond that

  • classifyStructured — one test per contract row, plus malformed JSON on one line, no output at all, truncated stream, and interleaved stderr. None may throw.
  • Resume loop — same sessionId across attempts; no --resume on attempt 1; exactly one budget unit per attempt; stops at maxAttempts; never resumes after PROCESS_FAILURE; the repeated-question guard still fires.
  • Contract tests, live — one per launcher, run on demand. They catch harness upgrades. cldx and cpx pass today; five others are unverified.
  • Integration — a delegation that lacks information resumes once then completes; timeout kills the child; abort leaves no orphan process.
  • The real check — re-run the 22-profile sweep. Classes A, B, C, D, E and G should disappear; class F is a prompt problem and stays. If the pass rate does not move well above 27%, this migration has not delivered, and the result must be reported as such.

Accepted loss

One capability goes: typing into a running turn

Watching is not lost — --output-format stream-json emits every assistant message and tool call as it happens. Tail the file. What goes is steering a turn that is already in flight. When you genuinely need that, launch that one profile in a terminal by hand. The orchestrator does not need to own a PTY so that you can occasionally rescue a run.
